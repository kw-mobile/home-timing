# 기여 기록과 최종 보고서 준비

목적은 작업할 때 **누가 무엇을 만들고 확인했는지** 남겨, 마지막에 기억이나 커밋 개수로 기여도를 추정하지 않게 하는 것입니다. 별도 보고서 양식은 정해지지 않았으며 아래 구조를 팀 기준으로 사용합니다.

개발 기록은 GitHub 이슈·PR·WORKLOG에서 관리합니다. Notion 신규 쓰기는 중단했으며, 기존 자료의 이전 위치와 보존 범위는 [GitHub 기록 전환](NOTION_SYNC.md)을 따릅니다.

## 기록의 역할

| 위치 | 남길 내용 | 시점 |
| --- | --- | --- |
| GitHub 이슈 | 요구사항·완료 기준·담당/참여 예정자·작업 범위 | 시작 전, 범위 변경 시 |
| PR 본문 | 변경 이유·최종 구현·실제 참여자별 역할·검증·한계 | PR 생성 시 작성, 작업 종료 전에 최신화 |
| PR 댓글 | 중요한 결정 변경·새 검증·리뷰 수정의 근거 | 해당 사건이 생겼을 때 |
| [WORKLOG](WORKLOG.md) | 날짜·실제 참여자·작업 요약·PR 링크 | 작업 완료 시 한 행, 병합/검증 후 필요 시 갱신 |

이슈 담당자는 계획이고 PR 참여자는 실제 수행 기록입니다. 진행 상태는 이슈, 자세한 설명은 PR에 두고 WORKLOG에는 다시 복사하지 않습니다. 같은 작업의 후속 수정은 기존 행을 갱신하고, 별도 검증·결정은 새 행으로 남깁니다. 짧은 PR은 최종 본문만으로 충분하며 형식적인 진행 댓글을 요구하지 않습니다. WORKLOG 표의 동시 수정으로 충돌이 나면 양쪽 작업 기록을 모두 보존합니다.

## 참여자별로 반드시 남길 것

PR 템플릿의 기여 표에 사람별로 아래 내용을 씁니다.

- 팀원 이름 또는 GitHub 계정. 같은 사람을 일관되게 표기합니다. 최종 팀 보고서를 작성할 때 참여자에게 이름·계정을 확인하고 보고서의 역할 분담 표에 연결합니다.
- 역할: 설계·구현·검증·리뷰 중 실제로 수행한 역할.
- 구체적 내용: 기능/화면/규칙과 수정한 파일 또는 코드 위치. ‘개발 참여’처럼 구분할 수 없는 표현은 쓰지 않습니다.
- 근거: 관련 커밋·파일·리뷰·검증 댓글 링크. 공동 구현은 각자의 부분을 구분합니다.

테스트 실행자와 구현자가 다르면 따로 적습니다. PR 작성자나 커밋 작성자라는 이유만으로 구현 전체를 맡았다고 판단하지 않습니다. AI가 초안을 작성했다면 사용 도구와 사람이 수행한 설계·수정·검증을 구분합니다. 참여자나 역할을 아직 모르면 ‘확인 필요’로 표시하고, **팀 보고서에 개인 기여로 반영하기 전에 확인**합니다. 기여 비율과 작업 시간은 근거 없이 산출하지 않습니다.

## PR 본문

저장소의 [PR 템플릿](../../.github/pull_request_template.md)을 사용합니다. 최소한 다음 질문에 답해야 합니다.

1. 어떤 요구사항/이슈를 왜 바꿨는가?
2. 사용자가 무엇을 할 수 있게 되었고, 핵심 구현은 어디에 있는가?
3. 누가 어떤 부분을 구현·설계·검증·리뷰했는가?
4. 어떤 커밋과 환경에서 무엇을 확인했고, 근거는 어디에 있는가?
5. 아직 동작하지 않거나 확인하지 못한 것은 무엇인가?

설계 선택에 대안이 있었다면 채택 이유를 남깁니다. 실패한 모든 시도를 나열할 필요는 없지만, 원인과 해결을 확인한 문제는 재현 조건·원인·수정·검증을 남깁니다. 본문은 최종 결과로 유지하고 중요한 이전 결정은 댓글에서 추적할 수 있게 합니다.

## PR 댓글

다음 상황에 댓글을 남깁니다. 새로운 정보 없이 같은 결과를 본문과 댓글에 반복하지 않습니다.

- **결정:** 기존 계획에서 범위·구조·데이터 계약이 바뀜. 이유·대안·영향과 갱신한 기준 문서 링크.
- **검증:** 다른 사람이 기기로 확인하거나 새로운 시나리오를 검증함. 실행자·앱 SHA·환경·절차·기대/실제·근거·한계.
- **리뷰 반영:** 어느 지적을 어떤 커밋으로 해결했고 무엇을 재확인했는지. 리뷰 스레드에서 답할 수 있으면 별도 댓글을 늘리지 않음.
- **문제 해결:** 재현 조건 → 확인된 원인 → 수정 커밋 → 재검증 결과. 원인 추정은 추정으로 표시.

예를 들어 검증 댓글은 아래 정보를 담습니다. 실제로 수행하지 않은 항목을 예시에서 복사해 성공으로 기록하지 않습니다.

```text
[검증] 실행자 / 앱 커밋 SHA
환경: 기기와 Android 버전 또는 CI URL
절차: 재현할 수 있는 입력·행동
기대 / 실제: 각각 구분, 성공·실패·미실행
근거: 로그·이미지·영상·테스트 결과 링크
미검증: 남은 조건
```

## 보고서에 모을 내용

| 보고서 항목 | 모을 근거 |
| --- | --- |
| 문제·목표·제출 범위 | [MVP](../MVP.md), 관련 이슈와 범위 결정 |
| 설계·기술 선택 | [아키텍처](../ARCHITECTURE.md), 설계 결정이 있는 PR |
| 실제 구현 기능 | 기능 PR, 관련 코드, 해당 SHA의 화면·사용 흐름 |
| 테스트·결과 | [검증 기준](../TESTING.md)에 맞춘 실제 결과와 실패/한계 |
| 역할·일정 | WORKLOG의 날짜·참여자와 PR의 기여 표, 계획 대비 변경 |
| 문제 해결·회고 | 원인과 재검증이 남은 PR 댓글, 미완성 기능과 개선 계획 |

스크린샷·영상은 앱 SHA·기기·시나리오를 식별할 수 있게 저장하고 PR에서 연결합니다. 필요할 때 `docs/report/evidence/`에 이미지를 추가하거나 팀이 관리하는 파일 링크를 사용합니다. 대용량 영상·APK·전체 로그를 Git에 계속 누적하지 않습니다. 로그인 정보·API 키·개인정보가 보이는 자료는 올리지 않습니다.

최종 보고서는 **실제로 확인된 기능과 실제 참여 내역**으로 작성합니다. 기획·미병합 PR·시연용 데이터·실서비스 검증을 구분하고, 구현하지 않은 기능은 계획/한계로 명시합니다.
